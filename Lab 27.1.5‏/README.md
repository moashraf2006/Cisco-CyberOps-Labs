## 📌 Overview

This lab introduces **log normalization**, the process of converting parts of log messages into a common and consistent format.

Log entries are generated by many different sources, including:

- Network devices
- Operating systems
- Applications
- Programmable devices
- Web servers
- Security monitoring tools

Because different sources use different terminology, delimiters, timestamp formats, and field structures, normalization is important when logs are collected at a centralized location.

In this lab, command-line tools are used to manually normalize log entries.

# 🧠 Background — Log Normalization

A file containing a time-sequenced stream of log entries is called a **log file**.

The syntax and format of log messages are often defined by the application developer. As a result, the terminology used by different sources can vary.

For example, the following terms may describe a successful user authentication event:

```text
login
logon
authentication event
user connection
```

A consistent terminology and format is especially useful when logs from multiple sources are collected by a centralized system.

### Normalization

**Normalization** refers to converting parts of a message, such as a log entry, into a common format.

```text
Different Log Sources
        │
        ├──────────────┐
        │              │
        ▼              ▼
 Different Formats   Different Terms
        │              │
        └───────┬──────┘
                ▼
         Log Normalization
                │
                ▼
       Common / Consistent Format
                │
                ▼
        Easier Log Analysis
```

# 🕐 Part 1 — Normalize Timestamps in a Log File

## 1️⃣ Unix Epoch vs Human Readable

Timestamps specify when a recorded event took place.

It is considered best practice in the lab to record timestamps in **UTC**, but timestamp formats can vary between log sources.

Two common timestamp formats are:

| Format | Description |
|---|---|
| **Unix Epoch** | Number of seconds since January 1, 1970 |
| **Human Readable** | Separate year, month, day, hour, minute, and second values |

Example:

```text
Human Readable:
Wed, 28 Jun 2017 13:27:19 GMT

Unix Epoch:
1498656439
```

### Why Use Both?

From a programmability perspective, Epoch is easier to work with because addition and subtraction operations are straightforward.

From an analysis perspective, Human Readable timestamps are easier for analysts to interpret.

# 🛠️ 2️⃣ Convert Epoch to Human Readable with AWK

AWK is a programming language designed to manipulate text files.

It is particularly useful for files containing multiple fields separated by a delimiter, making it suitable for processing log files.

Consider:

```text
2|Z|1219071600|AF|0
3|N|1219158000|AF|89
4|N|1220799600|AS|12
1|Z|1220886000|AS|67
5|N|1220972400|EU|23
6|R|1221058800|OC|89
```

### File Characteristics

- Fields are separated by `|`
- The file contains five columns.
- The third column contains the Unix Epoch timestamp.
- The source file contains an extra empty line at the end.

---

## 📂 Navigate to the Lab Files

```bash
cd /home/analyst/lab.support.files/
```

List the files:

```bash
ls -l
```

The directory contains:

```text
apache_in_epoch.log
applicationX_in_epoch.log
```

among other lab-support files.

---

## ⚙️ Run the AWK Conversion

```bash
awk 'BEGIN {FS=OFS="|"}
{$3=strftime("%c",$3)} {print}' applicationX_in_epoch.log
```

Example output:

```text
2|Z|Mon 18 Aug 2008 11:00:00 AM EDT|AF|0
3|N|Tue 19 Aug 2008 11:00:00 AM EDT|AF|89
4|N|Sun 07 Sep 2008 11:00:00 AM EDT|AS|12
1|Z|Mon 08 Sep 2008 11:00:00 AM EDT|AS|67
5|N|Tue 09 Sep 2008 11:00:00 AM EDT|EU|23
6|R|Wed 10 Sep 2008 11:00:00 AM EDT|OC|89
||Wed 31 Dec 1969 07:00:00 PM EST
```

---

## 🔍 Understanding the AWK Script

| Component | Purpose |
|---|---|
| `awk` | Invokes the AWK interpreter |
| `BEGIN` | Defines actions performed before processing input |
| `{}` | Defines actions for each input line |
| `FS` | Input field separator |
| `OFS` | Output field separator |
| `FS=OFS="|"` | Sets `|` as the delimiter |
| `$3` | Refers to the third column |
| `strftime()` | Converts time values into a formatted timestamp |
| `%c` | Specifies the Human Readable date/time format |

The script changes only the third field:

```awk
$3=strftime("%c",$3)
```

The remaining fields are preserved.

---

## ❓ Why Does the Extra Timestamp Appear?

The output contains:

```text
||Wed 31 Dec 1969 07:00:00 PM EST
```

The source file contains an empty line at the end.

AWK interprets the empty third field as:

```text
0
```

Unix Epoch `0` represents the beginning of the Unix Epoch.

Because the CyberOps Workstation is configured for EST (UTC -5), the displayed time becomes:

```text
Wed 31 Dec 1969 07:00:00 PM EST
```

### Answer

> The Unix Epoch timestamps were successfully converted to Human Readable format. Only the timestamp field was modified, while the other fields remained unchanged.

---

# 🧹 3️⃣ Remove the Extra Empty Line

Open the file with `nano`:

```bash
nano applicationX_in_epoch.log
```

Remove the empty line at the end of the file.

Then run the AWK command again:

```bash
awk 'BEGIN {FS=OFS="|"}
{$3=strftime("%c",$3)} {print}' applicationX_in_epoch.log
```

### Result

The output is now correct because the empty line has been removed.

No additional timestamp is generated.

# 🌐 Part 2 — Normalize Timestamps in an Apache Log File

Apache web-server logs can also be normalized using AWK.

The source file is:

```text
apache_in_epoch.log
```

Example entries:

```text
198.51.100.213 - - [1219071600] "GET /twiki/bin/edit/Main/Double_bounce_sender?topicparent=Main.ConfigurationVariables HTTP/1.1" 401 12846
198.51.100.213 - - [1219158000] "GET /twiki/bin/rdiff/TWiki/NewUserTemplate?rev1=1.3&rev2=1.2 HTTP/1.1" 200 4523
198.51.100.213 - - [1220799600] "GET /mailman/listinfo/hsdivision HTTP/1.1" 200 6291
198.51.100.213 - - [1220886000] "GET /twiki/bin/view/TWiki/WikiSyntax HTTP/1.1" 200 7352
198.51.100.213 - - [1220972400] "GET /twiki/bin/view/Main/DCCAndPostFix HTTP/1.1" 200 5253
198.51.100.213 - - [1221058800] "GET /twiki/bin/oops/TWiki/AppendixFileSystem?template=oopsmore&m1=1.12&m2=1.12 HTTP/1.1" 200 11382
```

---

## 📊 Apache Log Structure

The Apache log contains six entries.

The lab identifies seven fields:

| Field | Description |
|---:|---|
| 1 | IPv4 address of the web client |
| 2 | Unused field represented by `-` |
| 3 | Unused field represented by `-` |
| 4 | Unix Epoch timestamp |
| 5 | HTTP request information |
| 6 | HTTP status code |
| 7 | Response size in bytes |

The fields are separated by a **space**.

The timestamp is located in:

```text
Column 4
```

---

# ⚙️ 1️⃣ Initial AWK Attempt

Run:

```bash
awk 'BEGIN {FS=OFS=" "}
{$4=strftime("%c",$4)} {print}' apache_in_epoch.log
```

### Result

The timestamps are incorrectly converted to:

```text
Wed 31 Dec 1969 07:00:00 PM EST
```

---

## ❓ Why Did the Conversion Fail?

The timestamp in the Apache log is surrounded by square brackets:

```text
[1219071600]
```

The AWK script expects the timestamp to be a numeric Unix Epoch value.

Instead, `$4` contains:

```text
[1219071600]
```

The square brackets must therefore be removed before passing the value to `strftime()`.

---

# 🧹 2️⃣ Remove Square Brackets with `gsub()`

The adjusted AWK script is:

```bash
awk 'BEGIN {FS=OFS=" "}
{gsub(/\[|\]/,"",$4)}{print}{$4=strftime("%c",$4)}{print}' apache_in_epoch.log
```

The important action is:

```awk
gsub(/\[|\]/,"",$4)
```

This removes:

```text
[
]
```

from the fourth field.

---

## 🔎 Understanding `gsub()`

`gsub()` is an AWK internal function used to locate and substitute strings.

The expression:

```awk
gsub(/\[|\]/,"",$4)
```

contains three parameters:

### 1. Search Pattern

```text
/\[|\]/
```

This means:

```text
Find "[" OR "]"
```

The backslash escapes the square brackets so they are treated as literal characters.

### 2. Replacement

```text
""
```

An empty string means that the matched characters are removed.

### 3. Target Field

```text
$4
```

The operation is applied only to the fourth column.

# 🔄 Apache Normalization Workflow

```text
Apache Log
    │
    ▼
Identify Delimiter
    │
    ▼
Identify Timestamp Field
    │
    ▼
Timestamp = [1219071600]
    │
    ▼
Remove [ and ]
    │
    ▼
Timestamp = 1219071600
    │
    ▼
strftime()
    │
    ▼
Human Readable Timestamp
```

---

## ✅ 3️⃣ Verify the Corrected Script

Execute:

```bash
awk 'BEGIN {FS=OFS=" "}
{gsub(/\[|\]/,"",$4)}{print}{$4=strftime("%c",$4)}{print}' apache_in_epoch.log
```

The script now properly converts the timestamps.

The output contains **two lines for each log entry**:

```text
Original Entry
Normalized Entry
```

The first line contains the Unix Epoch timestamp, while the second line contains the Human Readable timestamp.

# 🛡️ Cybersecurity Relevance

Log normalization is a fundamental part of security monitoring.

Security environments often collect logs from many different technologies, each with its own:

- Timestamp format
- Field structure
- Delimiter
- Terminology
- Data representation

Without normalization, analysts may have difficulty comparing and correlating events.

### Example

```text
Source A:
login

Source B:
logon

Source C:
authentication event

Source D:
user connection
```

Normalization allows these events to be prepared for consistent analysis.

---

# ⚠️ Important Analyst Consideration

Manual normalization scripts must be tested carefully.

A poorly written normalization script can:

- Modify data incorrectly.
- Misinterpret fields.
- Produce incorrect timestamps.
- Introduce unexpected values.
- Directly affect the analyst's investigation.

The lab demonstrates this with:

```text
Empty line
   ↓
Interpreted as 0
   ↓
Unix Epoch 0
   ↓
Unexpected 1969 timestamp
```

and:

```text
[1219071600]
       ↓
Square brackets not removed
       ↓
Incorrect timestamp conversion
```

> 💡 **Always verify normalized output against the original log data.**
