In this lab, you will:

- **Part 1:** Investigate the attack with Sguil.
- **Part 2:** Use Kibana to investigate alerts.
- Identify the specific time of the attack on **2019-03-19**.
- Identify the infected Windows host and user.

- Correlate IDS alerts, network traffic, downloaded executables, and malware indicators.

---

## 🧠 Background / Scenario

In **March 2019**, network security monitoring tools alerted that a Windows computer on the network was infected with malware.

The investigation focuses on alerts and network activity associated with the attack on:

```text
2019-03-19
```

The investigation uses:

- **Sguil** to review IDS alerts and related network evidence.
- **Wireshark** to inspect packet data and export downloaded files.
- **Cisco Talos File Reputation Center** to investigate file hashes.
- **Kibana** to correlate and investigate additional alerts and network activity.
- **Zeek Hunting dashboards** to examine HTTP, DNS, SSL, and other protocol data.

> ℹ️ **Lab Note:** The alert IDs shown in the exercise are examples. Alert IDs on an individual Security Onion VM may be different.

## 🧩 Identify the Downloaded File

When binary data is viewed as text, the beginning of the file can contain a recognizable file signature.

The first characters observed are:

```text
MZ
```

`MZ` is associated with a Windows executable file, such as:

```text
.exe
.dll
```

Therefore, the HTTP response contained a Windows executable.

# 🧩 Legitimate Windows Traffic

Not every HTTP request associated with the infected host is necessarily malicious.

Two notable files are:

```text
CSPCA.crl
ncsi.txt
```

### `CSPCA.crl`

The lab identifies this as a request for the Microsoft certificate revocation list.

```text
/pki/crl/products/CSPCA.crl
```

### `ncsi.txt`

The lab identifies `ncsi.txt` as related to the **Network Connection Status Indicator**.

Windows uses this mechanism as a self-test to verify online connectivity.

This distinction is important during threat hunting:

```text
Observed HTTP Traffic
        │
        ├── Suspicious
        │     ├── test1.exe
        │     └── f4.exe
        │
        └── Expected Windows Activity
              ├── ncsi.txt
              └── CSPCA.crl
```

# 🔐 Cybersecurity Relevance

This lab demonstrates a realistic SOC investigation workflow where multiple security-monitoring sources are used to reconstruct an attack.

| Technique | Security Application |
|---|---|
| **Sguil Alert Hunting** | Review IDS alerts and identify attack activity |
| **Packet Inspection** | Examine source, destination, ports, and protocols |
| **HTTP Transcript Analysis** | Identify downloaded files and suspicious requests |
| **File Signature Analysis** | Identify executable files using magic bytes |
| **SHA256 Hashing** | Create a unique file identifier |
| **Threat Intelligence** | Check file hashes against malware reputation data |
| **RAT Detection** | Identify command-and-control activity |
| **SSL Certificate Analysis** | Detect connections associated with known malicious infrastructure |
| **Kibana Hunting** | Correlate alerts and network events |
| **Zeek HTTP Analysis** | Investigate web traffic and downloaded objects |
| **Zeek DNS Analysis** | Identify suspicious domains |
| **Geolocation** | Add geographic context to suspicious IP addresses |

# 🎯 Key Takeaways

- IDS alerts provide valuable starting points for incident investigations.
- A single alert may require packet-level analysis before its significance is understood.
- The first DNS alert may represent an IDS rule mismatch rather than malicious traffic.
- HTTP transcripts can reveal executable downloads.
- The `MZ` signature is a useful indicator of a Windows PE executable.
- SHA256 hashes can be used to query malware reputation services.
- Remcos RAT activity can be detected through characteristic network communication.
- Malware may use encryption, encoding, and packing to make detection and analysis harder.
- Multiple alerts can reveal different stages or components of the same attack.
- Kibana can provide additional context beyond what is immediately visible in Sguil.
- Not every connection from an infected host is malicious; expected Windows traffic must be distinguished from suspicious activity.
- DNS, HTTP, SSL, SMB, PE, and other Zeek datasets can be correlated to expand an investigation.
